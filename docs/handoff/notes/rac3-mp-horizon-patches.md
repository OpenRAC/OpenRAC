# Horizon Private Server: client-side patches for Up Your Arsenal, mapped onto the OpenRAC port

Research only, 2026-11-22. Source: a read of the Horizon-Private-Server organisation (27 repositories), mainly
`horizon-uya-patch` at `2993717`, plus `horizon-uya-plugin` (`d0d11ba`), `horizon-server` (`a262a79`) and `horizon-deadlocked-patch` (`02f9f22`).
Everything was read statically; nothing was run. No code was copied; our port is described in our own words.
How the patch was read: the C source, its per-level address tables (`patch/interop/*.c`) and the comments and commit
messages that give each fix's reason. Addresses below are the **Bakisi (level 40) overlay** values, PAL then NTSC-U, as the
patch lists them (every other level has its own offset); core-ELF addresses are marked "core".

## 1. Summary

- **Org:** 27 repositories. Client-side game patches live in **one** repository, `horizon-uya-patch` (UYA), with a sibling `horizon-deadlocked-patch`
  (Deadlocked) by the same author. The others are the server (`horizon-server`), the UYA/DL server plugins, DNS/DNAS, a map downloader, a map editor, bots, Discord bots and web/tools.
- **How the patch works:** it is not a binary patch of the disc. The server plugin writes a compiled payload into EE memory over the game's own RT memory-write
  messages and puts one jump at `0x00139E94` (PAL and NTSC-U alike) to run it every frame. The payload hooks `jal` call sites and pokes single instructions
  at about 60 address tables (per level and region), per region. That is why every item has addresses: we have the decompiled C instead, so we change the C.
- **Patch count:** 81 rows: 63 UYA client patches (a 14, b 3, c 14, d 32), 5 UYA server-compat rules that mirror the same client quirks (a 0, b 5, c 0, d 0), 13 Deadlocked functions named for reference (a 0, b 0, c 13, d 0).
  Overall: a 14, b 8, c 27, d 32. Many of the 32 "d" rows are options and modes (19 QoL toggles, game rules, custom modes and maps), not fixes.
- **What Horizon had to fix for UYA online** (the (a) group, 14): the late-packet lag-out, the "waiting for response" stall, the turret delay, game-time ordering, remote gadget-event timing,
  host-authoritative CTF flag, plus eight real game bugs that show up in online play (gadget class crash, kill stealing, dead shooting/jumping, flux wall sniping and niking, flux light leak, Metropolis barrier).
- **Not found:** no real anti-cheat in the client (only a MAC-based "real PS2 / PCSX2 / launcher" label sent to the server); no DNAS patch in the client (DNAS is
  answered by a DNS redirect to a replacement server, and the plugin ignores the signature report); no voice fix; no region/connection fix beyond the server-side join answer padding.
- **Licence:** every repository we would take from is MIT (Daniel Gerendasy, hashsploit, "Horizon"); 13 repos have no licence file at all and are not to be copied. Reference-only is what we do, and credit is still given.

## 3. Patches

Classes: **(a)** needed, a real game bug we must fix too; **(b)** handled differently because the port replaces that layer; **(c)** not applicable;
**(d)** nice extra for later. "How" is native: change the decompiled C or wrap a function in the port's host layer (`mp_net.c`, rows in `mp/libraries.tsv`); no binary patches.
Our reading of protocol.md/STATUS.md: the port replaces DNAS, Medius and the DME transport with the OpenRAC server relay (`PACKET_RELAY`), runs the retail lobby and room code on top
(8-slot DME tables, net time of 20 ms a frame when the DME clock is not steady, host silence flagged after 1.2 s), and two PAL clients already reach START together.
Anything that depends on the game clock, the late-packet tests or remote events is therefore exposed to our relay's behaviour.

## 4. Prioritised (a) items

Order is by crash risk first, then by what the first real two-player match will hit. For each: how, and how to confirm.

1. **Hero gadget moby class guard** (crash). After `CreateMoby` in the equip routine (three call sites), check that the moby's class is loaded; if not, destroy it and return NULL, which the game already reads as "retry later"; remember failed classes. Check other `CreateMoby` callers for the same missing check. Confirm: join a game on Marcadia Palace, equip every weapon.
2. **Remote gadget-event time clamp.** Wrap the gadget-event handler so a message's `ActiveTime` is clamped to now. Confirm: client A fires every weapon, client B sees the shots at once. This is where our relay latency shows first.
3. **Late-packet lag-out removal.** Work out what stamps the per-slot last-receive time in our relay path and make the lag-out test pass for live relayed peers (or return "fine"). Confirm: a 60 s two-client run with the relay delayed by 300 ms.
4. **"Waiting for response" stall removal.** Same method, same test.
5. **Turret delay fix and game-time ordering.** One-line delay branch in the turret net code; check where the port ticks the net update against game time.
6. **Kill stealing, dead shooting, dead jumping.** Three small guards in the decomp C (`hitPoints <= 0`, no-input timer while dead). Cheap, safe, and visible in the first deathmatch.
7. **Flux wall sniping and niking.** Extra collision flag on the shot-creation collision line for remote shots; corrected remote shot direction and hit position. Verify with two clients; do both together.
8. **Flux muzzle light leak.** Delete the old light before overwriting its id; matters because remote shots arrive in bursts.
9. **Host-authoritative CTF flag logic.** Replace the flag update with host-decides-logic over our relay (request message, host handler, no 250 ms delayed pickup, host-only 40 s return, no stale-copy pickups). Do it once CTF maps run on two clients and the stock logic is seen to misbehave.
10. **Metropolis death barrier.** Height test on `inBaseHack`. Low priority.

(b) items to keep in mind rather than patch: reliable delivery for kind 0x80 game messages in the relay (their flux UDP-to-TCP change); `LOBBY_PLAYER_INFO_REQUEST` for account id -1 must succeed in whichever layer answers it; the sized `JoinGameResponse` we already compare with Horizon (protocol.md 6.1).
